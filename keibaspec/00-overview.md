このフォルダはClaude Codeに渡す指示書一式。**フェーズごとに1ファイルずつ順に実行**し、各フェーズの完了条件を満たしてレビューを受けてから次へ進むこと。先のフェーズを勝手に先行実装しない。

## 目的
JRA-VAN DataLab のデータから、レースごとに馬の特徴量・条件フラグ・総合評価をまとめた「予想指数表」（参考画像: 函館6Rのスクショ）をHTML＋JSONで自動生成する。最終的に期待値アプリに接続し、出口を「印」ではなく「買い目」にする。

## 全体アーキテクチャ
```
[Windows VM on Mac]                    [Mac側]
VMware Fusion + Win11 ARM
  └ JV-Link + TARGET frontierJV
      └ CSV出力  ──共有フォルダ──▶  指数表ジェネレーター(Node.js/TS)
                                        parser → rules → scoring → render
                                          ├ HTML指数表
                                          └ スコアJSON → keiba-ev(期待値アプリ)
```
- 取得層: Windows VM上のTARGET（公式ソフト）でCSV出力。コードは書かない
- 生成層: Mac上で動くCLIツール。本指示書の実装対象はこちらのみ

## 共通仕様（全フェーズで遵守）

### データモデルの大原則（リーク防止）
内部モデルは **PreRaceData（発走前に見える情報）** と **PostRaceData（レース後に確定する情報）** を型レベルで分離する。
- PreRace: 出馬表, 近走成績, 血統, 調教, 想定ペース, 前日/当日オッズ
- PostRace: 当該レースの着順, 確定オッズ, 払戻, 確定ラップ, 次走成績

指数計算（rules/scoring）は**PreRaceDataしか受け取れないシグネチャ**にする。PostRaceDataはバックテストの答え合わせ専用。混ぜると検証時に未来情報による嘘の好成績が出る。後から直すのは困難なので最初から分離する。

### 技術スタック
- Node.js + TypeScript
- 出力: 静的HTML 1ファイル/レース（外部依存なし、インラインCSS）＋ スコアJSON
- 設定はすべて `config.json` に外出し（weight, 閾値, 色, softmax温度）

### ディレクトリ構成
```
src/
  parser/      # CSV/JSON → 内部モデル（複数CSV結合→PreRace/PostRaceモデルの3段構成）
  rules/       # 条件フラグ定義（1ルール1ファイル）
  scoring/     # スコア計算・印付与・勝率変換
  pedigree/    # 血統系統マスタ・適性テーブル
  render/      # HTML生成
  backtest/    # Phase 3で実装
schema/        # score-export.json 等の出力スキーマ
config.json
data/sample/   # サンプルデータ
out/           # 生成物
```

### 出力テーブルの列構成（HTML）
1. 馬番・馬名・記号（[B]=ブリンカー）・騎手（☆★▲△の減量記号込み）
2. 予想人気（1=黄, 2=青, 3=橙, 4-5=緑 の背景色）
3. 印（◎○▲△×）— スコア順に自動付与
4. 総合評価（S+ / S / A / B / C）
5. 性齢・ローテ（例: 牡3,中3-5-1,同2,B2 = 中3週、近走5→1着、同距離2走目、ブリンカー2走目）
6. 備考(マイナス)・備考(プラス)— 条件フラグ文字列を列挙
7. 前走・二前・三前の着順評価（1-3着=○, 4-5着=△, 6着以下=×, 圧勝=◎, B=ブリンカー着用走）
8. 父系・母父系（系統ごとに背景色）
9. 基本脚質（f=逃げ先行, m=差し, b=追込。通過順位履歴から推定）
10. 予想位置（脚質×枠×想定ペース）
11. 調教評価・調子（↗→↘）
12. 生産地・調教師

### 条件フラグ（ルールエンジン）
`rules/` に1ルール1ファイル。形式:
```ts
{ name: string, sign: 'plus'|'minus', weight: number,
  condition: (horse: PreRaceHorse, race: PreRaceInfo) => boolean }
```
初期実装するルール（10個目安）:
- マイナス: 延長△ / ダ替△(初ダ) / 増量△ / 後方△(追込×前有利) / ローテ△(中1週未満 or 半年以上)
- プラス: 同2◎ / 最内枠◎・内枠先行◎ / 減量◎ / 叩き2◎ / コース替◎ / 人気落ち◎ / 鞍上強化◎

### スコアリング
```
score = 基礎点(近走着順の加重平均、直近ほど重い)
      + Σ(plusフラグ weight) - Σ(minusフラグ weight)
      + 調教評価ボーナス
      + 血統適性(父系・母父系 × コース種別 × 距離帯)
```
- 総合評価: 閾値でS+/S/A/B/C
- 印: スコア上位から◎○▲△、明確に劣る馬に×
- 血統系統マスタとweight初期値は仮置きでよい（バックテストで育てる前提）

### スコアJSONエクスポート
```json
{
  "race_id": "202607040611",
  "race_info": { "course": "函館", "surface": "ダ", "distance": 1700,
                 "pace": "H", "condition": "良" },
  "horses": [
    { "number": 5, "name": "レッドフロイデ",
      "score": 82.5, "rank": "S+", "mark": "◎",
      "win_prob": 0.28, "place_prob": 0.55,
      "flags": { "plus": ["内枠先行◎"], "minus": [] } }
  ]
}
```
- `win_prob`: レース内スコアのsoftmax正規化（合計=1、温度はconfig）
- `place_prob`: 複勝圏内率。EVアプリが複勝・馬連系を扱うために単勝率と併せて出す（初期は簡易推定でよく、Phase 3でキャリブレーション）
- スキーマは `schema/score-export.json` に定義

### 手入力項目の割り切り
想定ペース（S/M/H）と馬場状態は自動推定しない。レース単位のCLI引数 or 設定ファイルで手入力とする。

## 将来構想: Phase 5（機械学習化）
Phase 4完了後の拡張として、scoring層をルールベースからLightGBM等の確率モデルに差し替える構想がある。設計上の含み:
- PreRace/PostRaceの型分離とバックテスト基盤は、そのままMLの特徴量/ラベル分離と評価基盤になる。**この2つはML移行後も使う前提で丁寧に作ること**
- scoring層は「PreRaceData → 各馬のwin_prob/place_prob」というinterfaceを守り、内部実装（ルール合算 or MLモデル）を差し替え可能にしておく
- 学習データはPhase 3用の一括CSV（5〜10年分）を流用する
- Phase 5は本指示書の範囲外。着手時に別途指示書を作る
